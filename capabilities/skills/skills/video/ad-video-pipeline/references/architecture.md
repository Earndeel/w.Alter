## Architecture (6 Modules)

```
Notion Kanban → VIDEO SCOUT → VIDEO ANALYZER → PROMPT ENGINEER
                                                      ↓
                                                  REVIEW (Lucas)
                                                      ↓
                                            GENERATOR → DELIVERY (Drive)
```

### Module 1: VIDEO SCOUT
- Takes a foreplay.co (or any video) URL from Notion
- Downloads the video with yt-dlp or ffmpeg (may need Webtop/CDP for anti-bot on foreplay.co)
- Runs `ffmpeg -i video.mp4 -vf "select='gt(scene,0.3)'" -vsync vframes shots/shot_%04d.jpg` for shot detection
- Extracts keyframes per shot: `ffmpeg -ss {timestamp} -i video.mp4 -vframes 1 -q:v 2 shots/keyframe_%04d.jpg`
- Measures: total duration, fps, aspect ratio, count of shots
- Output: `output/{video_id}/` with `shots/`, `meta.json`, `source_video.mp4`

### Module 2: VIDEO ANALYZER (V3 — Direct Video Input, NO FRAMES)
- Sends the full `.mp4` as base64 to OpenRouter with `qwen/qwen3.6-plus:free`
- LLM decomposes the video itself (no frame extraction needed)
  - **Shot-by-shot description**: framing, camera, lighting, subjects, text overlays
  - **Scores**: qualite, engagement, vente, global (1-10)
  - **Structure**: timestamps, shot types, transitions
  - **Recommendations**: what works, what to improve for Kling regeneration
- Videos >150MB auto-compressed: `ffmpeg -vf scale=720:1280 -crf 28`
- 5-retry exponential backoff on 429 (30/60/90/120/150s pauses), 180s timeout
- Output: structured text in `video_analysis` table (JSON scores + detailed analysis)
- Script: `modules/video_analyzer_v3.py` (replaces `video_analyzer.py`)

### Module 3: PROMPT ENGINEER — LLM-based Payload Generation (Multi-Model)

**HOW IT WORKS (V5 — April 2026, MULTI-MODEL):**
The payload is generated by the LLM (OpenRouter, `google/gemini-3-flash-preview`, temperature=0.1). Each video model has its own config directory with a preprompt + schema. The system is generic — Fal.ai is the unique provider, only the endpoint + prompt template + schema change per model.

#### Architecture: Model Registry

```
models/
  kling_v3/
    config.json    ← id, name, provider, modes (t2v/i2v), endpoints, params
    prompt.md      ← LLM preprompt (rules, decoupage, style constraints)
    - `kling_v3/schema.md` — API schema reference (markdown, NOT JSON — just text for LLM)
  runway_gen4/     ← add new models by creating a directory
    config.json
    prompt.md
    schema.md
```

**To add a new model:**
1. Create `models/<model_id>/` with `config.json`, `prompt.md`, `schema.json`
2. Dashboard auto-detects it via `GET /api/models`
3. Model appears in the dropdown selector

#### config.json format (SIMPLIFIED — final version):
```json
{
  "name": "Kling v3 Pro",
  "endpoint": "fal-ai/kling-video/v3/pro/text-to-video"
}
```
The `id` comes from the **directory name** (`models/kling_v3/`), NOT from config.json. `model_runner.list_models()` injects `cfg['id'] = name` at runtime. Only 2 fields the code uses: `name` (display) and `endpoint` (Fal.ai endpoint). No modes, no provider, no env_key — keep it minimal.

#### Core Module: `modules/model_runner.py`

Generic runner that loads any model config and handles generate/submit/sync:

```python
model_runner.py list                          # List all available models
model_runner.py generate --card_id 15 --model kling_v3  # Generate payload via LLM
model_runner.py submit --card_id 15 --model kling_v3    # Submit to fal.ai
model_runner.py sync --card_id 15                       # Sync job status
model_runner.py sync-all                                # Sync all active jobs
```

Internal flow:
1. `load_model(model_id)` → loads config + prompt + schema from `models/<id>/`
2. `get_card_context(card_id)` → loads analysis + comments from DB
3. `call_llm(preprompt, user_section)` → sends 4 sources to LLM, returns JSON
4. `submit(card_id)` → calls `fal_client.submit(endpoint, args)` using payload
5. `sync(card_id)` → polls `fal_client.status()` → saves result

#### API Endpoints (Generic, replaces old /api/kling/*):

- `GET /api/models` → list available video models with modes
- `POST /api/generate/<card_id>/<model_id>` → async LLM generation, returns `{task_id}`
- `GET /api/generate/status/<task_id>` → poll generation progress
- `GET /api/payload/<card_id>` → get saved payload `{model_id, payload}`
- `POST /api/payload/save/<card_id>` → save edited payload `{payload, model_id}`
- `POST /api/submit/<card_id>` → submit to fal.ai `{payload, model_id}`
- `POST /api/sync/<card_id>` → sync job status from fal.ai
- `POST /api/sync-all` → sync all active jobs
- `GET /api/jobs` → all cards with video model jobs
- `GET /api/result/<card_id>` → job result with video URLs

**Legacy `/api/kling/*` routes still work** for backward compatibility.

#### Database Schema (Generic Columns)

New columns on `video_analysis` (old `kling_*` columns kept for compat):

| Column | Type | Purpose |
|--------|------|---------|
| `model_id` | TEXT | Which model (e.g. `kling_v3`) |
| `model_payloads` | TEXT | Generated JSON payload |
| `job_status` | TEXT | `submitted`, `in_queue`, `in_progress`, `completed`, `failed` |
| `job_request_id` | TEXT | fal.ai request ID |
| `job_result` | TEXT | fal.ai result JSON |
| `job_error` | TEXT | Error message if failed |

**Migration pattern (check actual columns first):**
```sql
-- 1. Check real columns
PRAGMA table_info(video_analysis);
-- 2. Add new columns
ALTER TABLE video_analysis ADD COLUMN model_id TEXT DEFAULT 'kling_v3';
ALTER TABLE video_analysis ADD COLUMN model_payloads TEXT;

-- 3. Migrate data (only for columns that actually exist)
UPDATE video_analysis SET model_id='kling_v3',
  job_status=COALESCE(job_status, kling_status),
  model_payloads=COALESCE(model_payloads, kling_payloads)
  WHERE kling_status IS NOT NULL OR kling_payloads IS NOT NULL;
```
**Always run `PRAGMA table_info()` first** — the skill docs may reference columns that don't exist (e.g. `kling_error` was never created).

#### 4 Sources Injected to LLM (per model):
1. **Analysis JSON** — Complete scene-by-scene analysis from `video_analysis.analysis_text` (DB)
2. **Comments** — Client notes from `cards.comments_json` (product names, text overlays, instructions)
3. **Schema** — Model-specific API schema from `models/<id>/schema.json`
4. **Preprompt** — Model-specific rules from `models/<id>/prompt.md
```python
generate_payload(card_id) → {
    "endpoint": "fal-ai/kling-video/v3/pro/text-to-video",
    "arguments": {
        "prompt": null,  # or single scene description
        "multi_prompt": [{"prompt": "...", "duration": "5"}, {"prompt": "...", "duration": "3"}],
        "negative_prompt": "blur, distort, and low quality, male, men, masculine, boy",
        "cfg_scale": 0.5,
        "generate_audio": true/false,
        "aspect_ratio": "9:16",
        "shot_type": "customize",
        "duration": "10"
    }
}
```

#### Dashboard: Model Selector (V5 UI)
The dashboard header has a model selector dropdown (populated from `GET /api/models`). The detail panel's "Generate" tab includes:
- **Model dropdown** — choose which model to generate for
- **Generate Payload** — calls `/api/generate/<card_id>/<model_id>`
- **Submit to Fal.ai** — calls `/api/submit/<card_id>` with selected model
- **Sync** — sync single card status
- **Textarea** — shows/edit the generated JSON payload

The card badges now show `model_id: status` (e.g., `kling_v3: completed`).

#### LLM Details:
- Model: `google/gemini-3-flash-preview` via OpenRouter (was `qwen/qwen3.6-plus:free`)
- Temperature: **0.1** (deterministic output)
- Max tokens: 8000
- Timeout: **180s** per attempt
- Retries: **5** with exponential backoff (30s, 60s, 90s, 120s, 150s for 429 rate limits)

#### Preprompt Modal (Multi-tab Dashboard UI):
The dashboard Preprompt button now opens a multi-tab modal managing ALL static prompts:
- Tab 1: **Video Analysis** → `prompts/video_analysis_prompt.md`
- Tab 2: **Kling API Schema** → `prompts/kling_api_schema.json`
- Tab 3: **Kling Prompt** → `prompts/kling_prompt.md`

Each tab has its own textarea + Save button. Frontend polls the LLM generation every 4s for up to 400s.

#### Prompt Files (`prompts/` directory):
- `video_analysis_prompt.md` — System prompt for video analysis (LLM decomposes video → JSON)
- `kling_api_schema.json` — Kling v3 API documentation with embedded `{...}` JSON example for default params
- `kling_prompt.md` — Rules for Kling payload generation: decoupage max 15s, product swap, audio logic, female-only casting, multi_prompt vs prompt logic
- `README.md` — Documentation of each file

#### LLM Generation Details:
- Model: `qwen/qwen3.6-plus:free` via OpenRouter
- Temperature: **0.1** (deterministic output)
- Max tokens: 8000
- Timeout: **180s** per attempt
- Retries: **5** with exponential backoff (30s, 60s, 90s, 120s, 150s for 429 rate limits)
- Total worst case: ~600s (10 min) if heavily rate-limited
- Response is stripped of markdown code blocks, parsed as JSON
- Payload is auto-saved to `video_analysis.kling_payloads` in DB

#### Kling Rules (enforced by LLM via preprompt):
1. **Decoupage**: max 15s per payload. Video > 15s = split into multiple payloads
2. **Product Swap**: If video shows a product, replace it with client's product from comments
3. **Audio**: `generate_audio: true` ONLY if lip-sync/narration + client provided text in comments
4. **Multi-prompt**: Multiple cuts → `prompt: null` + `multi_prompt: [{"prompt":..., "duration":...}]`
5. **Visual only**: No metadata ("Scene 1:", "Camera:"). Describe what you see fluently
6. **Female-only casting**: Add "male, men, masculine, boy" to neg_prompt; describe only women
7. **cfg_scale**: 0.5-1.0 max (v3 constraint)

#### Async Pattern (CRITICAL):
Flask sync endpoints TIMEOUT waiting for LLM (Gunicorn/WSGI thread blocked).
Pattern: POST returns task_id immediately → frontend polls GET `/api/kling/generate/status/<task_id>` every 4s.
Background thread runs the LLM call. In-memory `_generate_tasks` dict tracks state.
If Flask restarts, pending tasks are lost but payload is saved to DB after completion.

### Module 4: REVIEW
- Presents the proposed Kling payload to Lucas
- Shows: original keyframes side-by-side with proposed prompts
- Lucas approves or requests modifications
- Modifications can target: specific shot prompts, duration, aspect ratio, mood
- Output: approved `kling_payload.json`

### Module 5: GENERATOR
- Takes approved payload
- If `@Element` references needed → generates reference images via Nano Banana 2 (`fal-ai/nano-banana-2`)
- Submits to Kling V3 Pro via fal.ai API:
  - `text-to-video Pro`: `mcporter call fal.generate_video model="kling-video/v3/pro/text-to-video" arguments={...}`
  - `image-to-video Pro`: for product-consistent shots
  - `image-to-video Standard`: `mcporter call fal.generate_video model="kling-video/v3/standard/image-to-video" arguments={...}`
- Polls until complete, downloads resulting MP4
- Output: `output/{video_id}/final.mp4`

### Module 6: DELIVERY
- Creates client subfolder in Google Drive
- Uploads final video: use Google Drive SDK with `MediaFileUpload`
- Updates Notion card status to "Livrée"
- Notifies Lucas with download/share link
