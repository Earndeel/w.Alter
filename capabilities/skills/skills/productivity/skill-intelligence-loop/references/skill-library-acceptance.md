# Skill-library acceptance: find, load, execute

Optimize reliable task execution per context cost, not the number of skills, archived files, or completed Curator runs. Fewer names and intact archives do not prove better retrieval or usable procedures.

Separate responsibilities: Curator periodically reads and understands the library, merges genuine overlaps without losing useful distinctions, and organizes catalogue names, descriptions and references. It is background library maintenance, not a runtime dependency. Runtime discovery, selective loading and workflow execution belong to Hermes/Walter; do not invoke Curator for individual user requests or make task execution depend on a curation pass. Never force merges merely to meet an archive or size quota.

Use a compact task-oriented discovery index; load only the relevant procedure and its necessary supporting references. Preserve all useful capabilities without placing their full documentation in the permanent prompt.

Before broad consolidation, build representative user-task cases and record the expected skill, required steps and constraints. Verify that each case finds the correct current skill without relying on a remembered obsolete name, loads sufficient procedural detail, and exercises the workflow safely with real outputs. Measure total discovery/loading calls and actual request footprint, not only entry counts.

Consolidation must preserve discoverability and operational completeness: redirects/source routes must resolve, unique commands and scripts must remain accessible, and the selected skill must clearly instruct how to use them. An oversized generic umbrella or a chain of archive lookups is a regression when it makes selection ambiguous or execution slower.

Do not respond to an inconclusive consolidation by repeatedly launching global passes. Stop structural churn, identify the failed acceptance case, and repair the narrow retrieval/loading/execution defect. Require before/after results before expanding the rollout.

Explain progress to Monsieur in terms of the intended behavior: lightweight permanent context, reliable skill selection, and correct execution. Keep internal job IDs, test-suite counts and archiving mechanics secondary unless requested.
