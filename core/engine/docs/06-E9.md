« Terminer la convergence de notre architecture avant de passer aux étapes suivantes de la vision. » Chaque

Fondation (contrôle final V1).

## Procédure d'un déplacement (`walter layout move`)

1. **Plan** : inventaire des références à l'ancien chemin et au lien `/opt/walter-<x>` (code, unités systemd, liens
   de commandes, configurations de l'instance, réglages Claude Code / Codex / moteur, contrats), dépôt git propre,
   unités concernées.
2. **Sauvegarde** dans `@instance/backups/changes/<date>-e9-<module>/` : catalogue, unités et fichiers qui seront
   réécrits (copie + empreinte), manifeste du déplacement.
3. **Déplacement** (`mv` dans le même système de fichiers, sans copie), lien de compatibilité à l'ancien chemin,
   liens `/opt/walter-<x>` et `/usr/local/bin/*` repointés directement sur le nouveau dossier, catalogue mis à jour.
4. **Références** : unités, configurations et code réécrits vers le nouveau chemin (frontière de chemin exacte ;
   documents d'historique laissés tels quels).
5. **Vérification** : `walter layout`, `walter check`, tests du module, unités redémarrées et actives, gardien du
   module, publication git à blanc, paquet de configuration de sauvegarde à blanc.
6. **Retour arrière** (`--rollback`) : lien retiré, dossier remis, fichiers sauvegardés restaurés, unités
   relancées ; essayé sur le premier déplacement de chaque famille.
7. **Commit** du module, du catalogue et de la documentation.

## Écarts assumés (pas un simple déplacement de dossier)

- **E9.5 bus et journal d'exécution** : `walter_memory/bus.py` dépend de la couche de connexion de Memory, et
  `walter_memory/logs.py` de son ingestion et de sa politique de confidentialité. Les sortir vers `core/` demande de
  scinder ces couches : c'est une séparation de code, exclue de E9 par la consigne (« pas de refonte fonctionnelle »).
  Contrats et cibles (`core/bus`, `core/observability`) restent déclarés ; schémas PG inchangés.
- **Session navigateur de core** (`browser_auth.py`, `browser_sites.json`, `bin/walter-browser`) → browse : son
  appel par le serveur MCP changerait d'interface ; à faire avec `core/interfaces`.
- **MCP / hooks → `core/interfaces`, gardiens → ops, scénarios → lab** : composants à l'intérieur du dépôt core
  (pas des modules) ; les déplacer change des chemins d'appel des harnesses (`~/.claude/settings.json`, Codex, moteur).
  Lot à part, avec E9.9.
- **Profils de harness** (`/opt/walter-profiles/*`) : gardés à leur place (décision de `config/soul/targets.toml`) ;
  la mémoire par dossier de Claude Code et Codex dépend de ce chemin.
- **Journaux** : faits le 11/11 (`@instance/logs`, exclus de restic) ; le code qui écrit encore par `~/.hermes/logs`
  (`walter_hook.py`, `browser_auth.py`, gardiens) passe par le lien → réécriture avec E9.9.
- **`~/.hermes/.env`** : reste vivant (cible de `walter-secrets-sync`, lu par `walter_memory/llm.py` et
  `walter-cloudflare`) ; le sortir = changement de Secrets (clés par `walter-secrets`), pas un déplacement.
- **E9.9** : liens de compatibilité retirés seulement après un cycle complet de redémarrage (des processus de longue
  durée tournent encore par les anciens chemins) et la réécriture des skills qui les citent.
