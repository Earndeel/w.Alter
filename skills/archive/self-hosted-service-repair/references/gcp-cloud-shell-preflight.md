# Google Cloud / Cloud Shell preflight

This reference records a safe, reusable access-discovery pattern. It is **not** a recipe for bypassing a failed SSH path.

## Discovery

1. Open the authenticated Google Cloud Console for the expected project.
2. Identify the VM by name, zone, status, and external IP; compare that IP with the service hostname.
3. Authorize Cloud Shell only when the task requires control-plane API calls.
4. Run read-only discovery first:

```bash
gcloud compute instances describe INSTANCE \
  --zone=ZONE --project=PROJECT --format=json
```

For a metadata-only summary, pipe JSON through a small parser that prints only:

- metadata key names;
- SSH usernames (never the key material);
- `enable-oslogin` / `block-project-ssh-keys` state;
- network tags and service-account identifiers.

## SSH validation

Use a one-shot, read-only command after confirming the target:

```bash
gcloud compute ssh USER@INSTANCE \
  --zone=ZONE --project=PROJECT --quiet \
  --command='id -un; hostname; docker ps --format "{{.Names}}|{{.Image}}|{{.Status}}"'
```

A key generated by `gcloud` may be written to project metadata while the guest still rejects it. The observed failure signature is repeated `Permission denied (publickey)` followed by `Could not SSH into the instance`. Metadata presence is not proof of guest access.

When that happens:

- stop the retry loop;
- do not modify containers, volumes, firewall rules, or boot configuration;
- do not reboot solely to force propagation;
- obtain an existing authorized account/key or move to a separately verified recovery procedure with a disk snapshot and rollback plan.

## Remote-screen interaction

If the authenticated console exists only on a remote Mac, take a screenshot after each navigation step and verify that a command is visibly present before pressing Enter. Retina screenshots and logical click coordinates may differ; test the coordinate scale on a harmless control. For terminal canvases, focus the prompt explicitly and use the screen bridge's combo endpoint for shortcuts rather than typing strings such as `ctrl+c` into the shell.

If the bridge reports healthy but the screenshot is an all-black 2880x1800 PNG of roughly 100 KB, treat the visual channel as unavailable (locked display or macOS Screen Recording/TCC), not as a valid console view. Likewise, an `osascript`/`System Events ... not allowed to send keystrokes` response means the keyboard channel is not verified. Do not send long base64 recovery scripts or press Enter blindly; ask the user to foreground/unlock the Mac and grant Screen Recording/Accessibility, or have them run this harmless read-only check manually and return its output:

```bash
gcloud compute instances list \
  --project=PROJECT \
  --filter='name=^INSTANCE$' \
  --format='table(name,zone,status,networkInterfaces[0].accessConfigs[0].natIP)'
```

Resume only after the project, zone, status, and target IP are visible; a bridge endpoint returning `ok`/`typed` alone is not execution proof.

Do not leave temporary cloud SSH keys or project metadata entries in place after maintenance. Remove only entries that were added for the maintenance session, preserving pre-existing access configuration.
